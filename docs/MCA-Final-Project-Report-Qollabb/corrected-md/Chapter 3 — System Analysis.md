# Chapter 3 — System Analysis

Chapter 3 — System Analysis
3.1 Functional Requirements
Functional requirements define the services that the proposed system must provide to its users. In the School Portal project, the functional requirements are organized into fifteen canonical modules. These modules represent the complete operational scope of the Multi-Tenant School Administration Management SaaS Platform and are designed to support school administration, tenant isolation, academic workflows, fee operations, examinations, reports, dashboards, activity tracking, audit evidence, and platform backup operations.
3.1.1 Authentication Module
The Authentication Module provides secure access to the School Portal system. It allows authorized users to log in, log out, reset forgotten passwords, manage password recovery, maintain sessions, and update their own profile information. Since the system supports multiple user roles, authentication acts as the first control point before role-based access and tenant-based authorization are applied. Every user, including Super Admin, School Admin, Teacher, and Accountant, must pass through this module before accessing protected platform features.
3.1.2 School Management Module
The School Management Module is responsible for managing tenant schools within the platform. It allows the Super Admin to create, view, update, activate, deactivate, and search school records. Each school acts as a tenant in the SaaS model, and school-specific operational data is linked to the corresponding school identity. This module is limited to the Super Admin because tenant creation and platform-level school administration must remain centralized and controlled.
3.1.3 School Settings Module
The School Settings Module allows each school to maintain its own institutional configuration. It includes school profile details, logo management, contact information, academic settings, attendance settings, and grading settings. These settings help personalize the operational environment for each tenant while keeping the core application shared. School Admin users manage this module for their own school only, ensuring that one school cannot change another school’s configuration.
3.1.4 User Management Module
The User Management Module supports the creation and administration of system users. It allows authorized administrators to create users, edit user records, reset passwords, activate or deactivate users, and assign appropriate roles. Super Admin users can manage platform users according to platform rules, while School Admin users can manage users within their own school. The module supports School Admin, Teacher, and Accountant user types for school-level operations and ensures that user assignment remains tenant-safe.
3.1.5 Role & Permission Module
The Role & Permission Module controls access to system features through a fixed role-based access control model. The system supports four canonical roles: Super Admin, School Admin, Teacher, and Accountant. Role and permission records are system-managed, and the application does not allow custom role creation, deletion, or renaming in the MVP scope. The module allows constrained permission mapping where permitted, while policies, tenant context, record ownership, and service-layer checks continue to decide whether a user may access or modify specific records.
3.1.6 Academic Structure Module
The Academic Structure Module manages the academic organization of a school. It includes academic years, academic terms, teacher profiles, classes, sections, and subjects. School Admin users can manage these records for their own school, while Teacher users can view only assigned classes, sections, or subjects according to their teacher profile assignments. This module provides the foundation for student enrollment, attendance, examination, and reporting workflows by defining the academic structure on which other modules depend.
3.1.7 Student Management Module
The Student Management Module handles student registration, student profiles, enrollment management, initial class and section assignment, status management, and private student photo management. School Admin users can manage student records within their own school. Teachers receive limited read-only access to students connected to their assigned sections or subjects, while Accountants do not access the full student management module directly and only perform limited student lookup during authorized fee workflows. Student photos are handled as private records and are not exposed to unauthorized users.
3.1.8 Attendance Management Module
The Attendance Management Module supports daily attendance, bulk attendance entry, attendance history, attendance search, monthly operational summaries, and authorized correction of retained attendance records. School Admin users can manage attendance for eligible students in active sections of their own school. Teachers can mark and correct attendance only for sections directly assigned to their active teacher profile. Attendance records are retained and corrected rather than deleted, preserving operational history and audit evidence.
3.1.9 Fee Management Module
The Fee Management Module manages fee categories, fee structures, student fee assignments, fee collection, receipt generation, payment tracking, outstanding balance views, and local sandbox transaction workflows. School Admin users can manage fee setup, assignments, collections, receipts, history, and balances for their own school. Accountant users can perform fee collection, receipt, payment history, outstanding balance, and sandbox transaction workflows, but they cannot configure fee categories, fee structures, or student fee assignments. The system does not implement a production payment gateway in the current scope.
3.1.10 Examination Management Module
The Examination Management Module supports exam setup, exam subject assignment, grade scale management, teacher-scoped marks entry, grade calculation, result processing, and operational report card view and print workflows. School Admin users manage exam setup, subject assignment, result processing, grade scales, and report card generation for their own school. Teachers can enter marks, review assigned results, and access operational report cards only for assigned class and subject scope. Accountant users do not access examination workflows.
3.1.11 Reporting Module
The Reporting Module provides operational reports across student, attendance, fee, and examination areas. Super Admin and School Admin users may also access authorized school summary and user summary reports where permitted. It supports filters, search, pagination, CSV export, and browser print for printable report views. Reports are role-aware and tenant-aware, meaning each user receives only the data that is permitted by role, tenant, assignment, and policy boundaries. Super Admin reports are platform-level and aggregate-focused, while School Admin, Teacher, and Accountant reports are restricted to their permitted school, class, assigned, or financial context. Activity logs, audit trail, and backup management are provided through System Operations, not the Reports hub.
3.1.12 Dashboard & Analytics Module
The Dashboard & Analytics Module provides real-time operational insights through role-specific dashboards. It includes statistics cards, charts, alerts, recent activity, and quick actions. Super Admin users view platform-level school, user, activity, audit, and backup summaries. School Admin users view school-level student, attendance, fee, examination, and activity summaries. Teachers view assigned class, attendance, marks-entry, and examination information, while Accountants view fee collections, outstanding fees, recent transactions, and receipt summaries.
3.1.13 Activity Log Module
The Activity Log Module records user activities performed in the system. It tracks events such as login, logout, create, update, delete, attendance actions, fee operations, examination actions, and report access. Super Admin users can review platform-wide activity logs, while School Admin users can review activity logs related to their own school only. This module supports transparency and helps administrators understand who performed operational actions within the application.
3.1.14 Audit Trail Module
The Audit Trail Module records data modifications in an immutable manner. It captures old values, new values, user identity, timestamp, IP address, and user agent where applicable. Audit records are used to preserve accountability for important changes across the platform. Super Admin users can view platform-wide audit records, while School Admin users can view only their own school’s audit records. The module is designed for traceability and compliance-style evidence within the academic project scope.
3.1.15 Backup Management Module
The Backup Management Module manages manual backup operations, backup history, and backup logs. It provides the Super Admin with a platform-level backup dashboard and backup history records. This module is restricted to the Super Admin only, because backup operations affect platform-level data and must not be available to tenant-level administrators. School Admin users may access Activity Logs and Audit Trail for their own school, but they do not access Backup Management.
3.2 Non-Functional Requirements
3.2.1 Security
Security is a central non-functional requirement because the system stores school, student, user, attendance, financial, examination, and audit-related information. The application must enforce authentication, authorization, CSRF protection, request validation, password hashing, session security, file upload validation, and tenant isolation. The tenant boundary is especially important because the system follows a shared application and shared database model. Therefore, every tenant-owned business record must be isolated using the school identifier and protected through middleware, global scopes, policies, and service-layer validation.
3.2.2 Performance
Performance is required to ensure that school administrators, teachers, and accountants can complete daily operations without delay. The system must support efficient database access through indexes, pagination, eager loading, query optimization, and prevention of unnecessary N+1 queries. Since the application includes list views, filtered reports, dashboards, attendance workspaces, fee screens, and examination result views, the system must avoid large unfiltered queries. The performance objective is not to provide artificial benchmark claims, but to use standard Laravel and database design practices that keep routine operations responsive.
3.2.3 Scalability
Scalability is required because the platform is designed as a multi-tenant SaaS application where multiple schools can operate on a single application and database. The chosen single-database multi-tenant model supports cost-effective scaling within the MCA project scope by reducing infrastructure duplication. New schools can be onboarded as tenants without deploying a separate application instance for each school. The layered monolithic design also allows modules to be developed and maintained independently while still being part of one deployable Laravel application.
3.2.4 Maintainability
Maintainability is required so that the project can be understood, extended, tested, and explained during academic evaluation and future development. The application follows a layered structure in which Blade views handle presentation, routes map requests, middleware applies authentication and tenant context, controllers remain thin, Form Requests validate input, services contain business workflows, models manage persistence, and policies enforce authorization. This separation of concerns reduces duplication, keeps business rules away from controllers, and makes the code easier to review and modify.
3.2.5 Usability
Usability is required because the target users are school administrators, teachers, and accountants who need simple operational screens for routine tasks. The interface uses Blade templates and Bootstrap 5 to provide browser-based forms, dashboards, tables, reports, charts, and navigation. Role-specific menus and dashboards reduce confusion by showing users only the workflows relevant to their responsibilities. The system is intended to be usable from a standard web browser without requiring a mobile application in the current scope.

3.4 Feasibility Study
A feasibility study evaluates whether the proposed system can be developed and operated successfully within the given technical, economic, and operational constraints. For the School Portal project, feasibility is assessed in relation to the selected Laravel stack, open-source development tools, multi-tenant SaaS architecture, fixed role model, and browser-based deployment model.
3.4.1 Technical Feasibility
The project is technically feasible because it is developed using Laravel 13, PHP 8.4, MySQL 8, Blade templates, and Bootstrap 5. These technologies support web-based application development, structured routing, middleware, validation, service classes, policies, Eloquent models, relational data storage, and responsive user interfaces. The system architecture follows a layered monolithic design, which is suitable for an academic MCA project because it demonstrates professional engineering practices while keeping the application understandable and manageable.
The multi-tenant design is also technically feasible because it uses native Laravel mechanisms rather than an external tenancy package. Tenant isolation is implemented through school_id, TenantContextMiddleware, TenantContext, the BelongsToTenant trait, Eloquent global scopes, policies, and service-layer checks. This approach allows the system to maintain one shared application and one shared database while still separating tenant-owned records. Since the architecture documents clear boundaries for authentication, authorization, tenant resolution, and data access, the project can be implemented and evaluated reliably.
3.4.2 Economic Feasibility
The project is economically feasible because it uses widely available and open-source technologies. Laravel, PHP, MySQL, Bootstrap, and standard web server components reduce licensing cost and make the system suitable for academic and demonstration purposes. The single-application, single-database, multi-tenant deployment model also reduces infrastructure duplication because each school does not require a separate deployed application instance or database server.
From the viewpoint of schools, the SaaS model can reduce manual administrative effort, spreadsheet dependency, and duplicated data handling. The project does not depend on paid external services such as a production payment gateway, SMS gateway, or mobile app store deployment in the current scope. Fee transactions are handled through a local sandbox workflow only, which keeps the academic project economically manageable while still demonstrating the fee collection process.
3.4.3 Operational Feasibility
The project is operationally feasible because it supports the actual working roles commonly required in school administration. Super Admin users manage platform-level concerns, School Admin users manage school operations, Teacher users handle assigned academic tasks, and Accountant users handle fee-related workflows. This role separation makes the system easier to operate because each user receives access to the modules needed for their responsibilities.
The browser-based interface also improves operational feasibility because users can access the system through standard web browsers without installing a separate desktop or mobile application. Dashboards, forms, reports, search screens, filters, pagination, and role-specific menus support routine school workflows. The system avoids unnecessary complexity such as custom role creation, parent portals, student portals, SMS integration, and production payment gateway integration in the MVP scope, allowing the implemented system to remain focused and demonstrable.
3.5 System Architecture Overview
The School Portal system follows a layered monolithic architecture. In this architecture, the application is deployed as a single Laravel application, but responsibilities are separated into clear internal layers. The request begins at the browser, passes through routes and middleware, reaches the controller, is validated through Form Requests, is processed through service classes, interacts with Eloquent models, and finally persists or retrieves data from the MySQL database. This structure can be summarized as Presentation Layer → Controller Layer → Service Layer → Model Layer → MySQL Database.
The Presentation Layer is implemented using Blade templates and Bootstrap 5. It provides forms, dashboards, reports, charts, tables, navigation, and printable views. The Controller Layer handles HTTP requests and responses but remains thin by delegating business logic to services. The Service Layer contains workflow processing, transaction management, and business rule enforcement. The Model Layer uses Laravel Eloquent ORM to represent database entities, relationships, casts, and query scopes. The Database Layer uses MySQL 8 to store platform, tenant, academic, student, attendance, fee, examination, reporting, logging, audit, and backup-related records.
Tenant isolation is handled through TenantContextMiddleware and related tenancy components. After a user is authenticated, TenantContextMiddleware validates the user’s role, status, school_id, and school state. A Super Admin operates under explicit Platform context, while school-level users operate under Tenant context for their assigned school. Tenant-owned models use the BelongsToTenant trait and global scope so that queries are automatically restricted to the active school context. Policies and service-layer checks further ensure that a permission code alone cannot bypass tenant ownership, assigned-class restrictions, lifecycle rules, or role boundaries.
Authorization is enforced using Laravel policies, gates, middleware, role-permission mappings, and service checks. This layered approach means that access is not decided at only one point in the application. Authentication verifies identity, role-permission mapping determines whether an action may be attempted, policies evaluate record and role boundaries, and services revalidate tenant and workflow rules before writing data. This design supports secure school-level operations while still allowing authorized Super Admin platform operations.
3.6 Data Flow Diagram — Level 0
The Level 0 Data Flow Diagram represents the School Portal system as a single process interacting with external users and the database. The main external actors are Super Admin, School Admin, Teacher, and Accountant. Each actor sends requests to the School Portal system through the browser interface. These requests may include login credentials, school administration actions, user management operations, student records, attendance entries, fee collection details, examination marks, report filters, activity log requests, audit log requests, or backup actions depending on the actor’s role.
At this level, the School Portal system receives user input, authenticates the user, resolves the tenant or platform context, applies authorization rules, processes the requested workflow, and communicates with the MySQL database. The database stores user accounts, schools, school settings, academic structures, student records, attendance records, fee records, examination records, report-related data, activity logs, audit trails, and backup logs. The system returns dashboards, forms, confirmations, reports, receipts, audit views, or error responses back to the actor based on the request outcome.
The Level 0 view emphasizes that all user roles interact with one centralized SaaS application while data separation is handled inside the system. School-level users do not directly choose or override tenant ownership. Instead, tenant context is derived from the authenticated user and enforced through the application layers. This makes the context diagram useful for explaining the overall boundary between users, the application process, and persistent storage.

3.7 Data Flow Diagram — Level 1
The Level 1 Data Flow Diagram decomposes the School Portal system into major internal processes. The first process is Authentication, where users submit credentials and the system validates identity, manages sessions, supports password recovery, and redirects users to role-specific dashboards. After authentication, the system resolves whether the user operates in Platform context or Tenant context.
The second process is Tenant Management. This includes school management by the Super Admin, school settings by the School Admin, user management, role assignment, and role-permission boundaries. Tenant Management ensures that schools are onboarded as separate tenants and that users are connected to the correct school and role. It also ensures that tenant-scoped users cannot perform platform-level operations.
The third process is Academic Operations. This includes academic years, academic terms, teacher profiles, classes, sections, subjects, student registration, student enrollment, attendance, and examination-related academic workflows. School Admin users manage academic and student records for their own school, while Teachers interact with assigned sections, subjects, attendance, marks entry, and assigned reports. These flows depend strongly on tenant context, active academic year, class and section relationships, and teacher assignment boundaries.
The fourth process is Financial Operations. This includes fee categories, fee structures, student fee assignments, fee collection, receipts, payment history, outstanding balances, and sandbox payment transaction records. School Admin users manage setup and assignment, while Accountants perform collection and related financial workflows. The financial process stores retained fee payment and transaction records and produces receipts and outstanding balance views.
The fifth process is Examination. This process includes exam setup, exam subject assignment, grade scale management, marks entry, result calculation, report card generation, and report card printing. School Admin users manage the full own-school examination workflow, while Teachers perform marks entry and review only within their assigned class and subject scope. The system calculates result-related values server-side and preserves retained academic result history.
The sixth process is Reporting. This includes student reports, attendance reports, fee reports, examination reports, and authorized school or user summary reports for Super Admin and School Admin roles. CSV export and browser-print views are supported where implemented. Dashboard analytics provides chart-based summaries for authorized roles. Activity log review, audit trail review, and backup history are handled through the separate System Operations workspace rather than the Reports hub. Reports are generated through filters and role-specific authorization. The reporting process does not expose data outside the user’s tenant, assignment, or platform boundary.

3.8 Use Case Diagram Overview
The Use Case Diagram for School Portal includes four primary actors: Super Admin, School Admin, Teacher, and Accountant. Each actor interacts with the system according to a defined responsibility boundary. All actors share common authentication and profile-related use cases such as login, logout, password reset, session access, dashboard access, and profile update. After authentication, use cases diverge according to role and authorization rules.
The Super Admin actor performs platform-level use cases. These include managing schools, viewing platform dashboard information, managing platform users where permitted, managing constrained role-permission mappings, viewing platform activity logs, viewing platform audit trails, accessing platform reports, and managing backup operations. The Super Admin operates in explicit Platform context and does not act as a normal school tenant user.
The School Admin actor performs tenant-level school administration use cases. These include managing school settings, managing school users, assigning permitted school roles, managing academic years and terms, maintaining teacher profiles, managing classes, sections, and subjects, registering and managing students, managing enrollments, marking or correcting attendance where authorized, configuring fee categories and structures, assigning fees, collecting fees, managing examinations, processing results, generating report cards, viewing school dashboards, accessing school reports, viewing own-school activity logs, and viewing own-school audit trails. Backup Management is not included in the School Admin use cases.
The Teacher actor performs assigned academic use cases. These include viewing assigned academic records, viewing limited student records for assigned sections or subjects, marking attendance for directly assigned sections, correcting permitted attendance records, entering marks for assigned subjects, reviewing assigned results, viewing operational report cards within assigned scope, and accessing assigned class reports. The Teacher role does not manage schools, users, role permissions, fee workflows, backup operations, or unassigned records.
The Accountant actor performs financial use cases. These include viewing the accountant dashboard, searching permitted student fee records through fee workflows, collecting fees, generating receipts, viewing payment history, reviewing outstanding balances, viewing sandbox transaction evidence, and accessing financial reports. The Accountant role does not manage academic setup, attendance, examination setup, student administration, role-permission management, audit logs, activity logs, or backup operations.
The use case view demonstrates that School Portal is not a generic unrestricted administration panel. It is a role-based and tenant-aware system where each actor receives only the use cases needed for their operational responsibility. The diagram should show the four actors connected to their permitted use cases, with shared authentication use cases at the top and role-specific use cases grouped by platform, school operations, teaching operations, and financial operations.
