# Chapter 4 — System Design

Chapter 4 — System Design
4.1 System Architecture Design
System design defines how the proposed system is organized internally so that the functional and non-functional requirements identified during system analysis can be implemented in a structured manner. The School Portal project follows a layered monolithic architecture. This means that the application is deployed as a single Laravel application, but its responsibilities are divided into clear layers such as presentation, routing, middleware, controllers, validation, services, models, and database storage. This architecture was selected because it provides a balance between simplicity, maintainability, security, and academic clarity.
The overall design of the system begins with the browser-based user interface. Users interact with the application through Blade templates styled with Bootstrap 5. The interface contains login forms, dashboards, data-entry screens, tables, filters, reports, charts, receipts, and printable report views. These screens do not directly access the database. Instead, each user action is submitted to Laravel routes, which map the request to the correct controller method and apply the required middleware.
The middleware layer is a critical part of the system architecture. It is responsible for authentication, session validation, tenant context resolution, and route protection. After the user is authenticated, the TenantContextMiddleware establishes whether the request belongs to a platform-level Super Admin context or a tenant-level school context. This tenant context is then used throughout the request lifecycle to restrict school-owned data. The middleware therefore acts as a security gate before controllers, policies, services, and models perform their own checks.
The controller layer handles HTTP requests and responses. Controllers are designed to remain thin and do not contain large business workflows. Their purpose is to receive the validated request, call the appropriate service, and return the correct view, redirect, report, or response. Input validation is handled through Laravel Form Requests wherever applicable. This separation improves maintainability because validation rules, controller flow, and business processing are not mixed into one large block of code.
The service layer contains the main workflow logic of the application. Services are responsible for business operations such as school creation, school setting updates, user management, academic record validation, student registration, attendance marking, fee collection, examination result processing, report generation, activity logging, audit logging, and backup history handling. The service layer also enforces business rules that cannot be trusted to the user interface alone. For example, school ownership, active status, assigned teacher scope, and fee workflow restrictions must be validated before a database write is allowed.
The model layer uses Laravel Eloquent ORM to represent database tables and relationships. Models define relationships such as a school having many users, students, classes, fee records, exam records, logs, and audit entries. Tenant-owned models use the BelongsToTenant approach so that tenant filtering can be applied consistently. The MySQL 8 database layer stores all platform, academic, student, attendance, fee, examination, reporting, logging, audit, and backup-related information.
This layered design supports secure multi-tenant behavior. A school-level user is not allowed to directly control the school_id from the browser. Instead, the active school is derived from the authenticated user and TenantContext. Policies, global scopes, service checks, and database relationships work together to ensure that a user from one school cannot read or modify records belonging to another school. The design therefore follows a defense-in-depth approach instead of depending on only one access-control point.

4.2 ER Diagram and Database Overview
The database design of School Portal follows a single-database, shared-schema, multi-tenant model. In this model, all schools use the same application and the same MySQL database schema, but tenant-owned records are separated using the school_id column. The school_id value identifies the owning school for strict tenant-owned business records. Platform-level records such as roles and permissions are shared catalog records, while Super Admin identity and platform events may use a null school_id where explicitly documented.
The database contains 28 tables grouped into seven logical areas: Platform, Academic, Students, Attendance, Fees, Examinations, and System. This grouping improves readability and helps explain the relationship between system modules and physical database storage. It also supports modular development because each functional area maps to a predictable set of tables.
The Platform group contains schools, school_settings, users, roles, permissions, and role_permissions. The schools table acts as the tenant registry and stores one row for each school tenant. The school_settings table stores school-specific configuration. The users table stores authenticated users and links school-level users to one school through school_id. The roles, permissions, and role_permissions tables support the fixed RBAC model used by the application.
The Academic group contains academic_years, academic_terms, classes, sections, subjects, and teachers. These tables define the academic organization of a school. Academic years and terms define time periods. Classes and sections define the structure in which students are enrolled. Subjects represent the academic subjects taught in each school. The teachers table represents teacher profile records linked to eligible teacher-role users.
The Students group contains students and student_enrollments. The students table stores student master information such as admission number, name, guardian details, admission date, status, and private photo path. The student_enrollments table connects a student to an academic year, class, section, roll number, enrollment date, and enrollment status. This separation allows the student record to remain stable while class and section assignment can change across academic years.
The Attendance group contains the attendances table. This table stores daily attendance records for students. It links each attendance entry to the school, student, academic year, class, section, attendance date, status, remarks, and the user who originally marked the attendance. Attendance is treated as retained operational history and is corrected rather than casually deleted.
The Fees group contains fee_categories, fee_structures, student_fees, fee_payments, and payment_transactions. Fee categories define fee names. Fee structures define fee amounts for academic years and classes. Student fees represent assigned fee obligations. Fee payments represent receipt-level payment history. Payment transactions store transaction-level references used by the local sandbox transaction workflow. This group supports school-level fee setup, assignment, collection, receipt generation, outstanding balance tracking, and financial reporting.
The Examinations group contains exams, exam_subjects, exam_results, grade_scales, and report_cards. Exams define examination events. Exam subjects connect exams with subjects and classes. Exam results store marks obtained by students. Grade scales define school-specific grade ranges. Report cards store generated summary records for students. This design supports exam setup, marks entry, result processing, grade calculation, and operational report card printing.
The System group contains activity_logs, audit_logs, and backup_logs. Activity logs record user actions such as login, create, update, report access, attendance entry, fee collection, and examination workflows. Audit logs record data-change evidence such as old values, new values, event type, actor, timestamp, IP address, and user agent. Backup logs record platform backup operations and are restricted to Super Admin access.

4.3 Key Table Structures
The schools table stores tenant school records. Its major fields include id, name, code, email, phone, address, city, state, country, postal_code, principal_name, website, status, deactivated_at, deactivation_reason, created_at, updated_at, and deleted_at. The code and email fields are unique at platform level. The status and deactivation fields allow schools to be activated or deactivated without deleting tenant data. The deleted_at column supports soft deletion where applicable, although routine deletion is not treated as a normal operational action.
The users table stores authenticated application users. Its important fields include id, school_id, role_id, name, email, email_verified_at, password, phone, status, last_login_at, remember_token, created_at, updated_at, and deleted_at. The school_id value is nullable because Super Admin users operate at platform level and therefore have school_id as null. School Admin, Teacher, and Accountant users require a school_id. The email field is globally unique so that the login process can identify the user before tenant context is established.
The students table stores student master records. Its major fields include id, school_id, admission_no, first_name, last_name, gender, date_of_birth, photo_path, guardian_name, guardian_phone, guardian_email, address, admission_date, status, created_at, updated_at, and deleted_at. The admission number is unique within a school rather than across the entire platform. The photo_path is treated as private storage because student photos are sensitive records. The status field supports active, inactive, transferred, or graduated states.
The student_enrollments table tracks the academic placement of a student. It includes id, school_id, student_id, academic_year_id, class_id, section_id, roll_no, enrollment_date, status, created_at, and updated_at. This table connects a student with the academic year, class, and section for a particular enrollment period. It also stores the roll number within the class and section context. This design allows one student record to be reused across academic years while maintaining separate enrollment history.
The attendances table stores daily attendance records. Its key fields include id, school_id, student_id, academic_year_id, class_id, section_id, attendance_date, status, remarks, marked_by, created_at, and updated_at. The status field can represent values such as present, absent, leave, late, or holiday. The marked_by field records the user who originally created the attendance entry. Attendance is linked to academic and class context so that reports can be generated by date, class, section, and student.
The student_fees table stores fee obligations assigned to students. Its fields include id, school_id, student_id, fee_structure_id, academic_year_id, amount, discount_amount, payable_amount, paid_amount, balance_amount, due_date, status, created_at, updated_at, and deleted_at. This table separates the assigned amount, discount, payable amount, paid amount, and remaining balance. The status field supports payment states such as pending, partial, paid, waived, or cancelled.
The fee_payments table stores fee collection receipts. Its fields include id, school_id, student_fee_id, student_id, receipt_no, amount_paid, payment_date, payment_mode, status, received_by, remarks, created_at, and updated_at. The receipt number is unique within a school. The payment_mode field supports modes such as cash, card, UPI, bank transfer, and sandbox gateway. This table is treated as financial history and is not designed for casual hard deletion.
The exams table stores examination master records. Its major fields include id, school_id, academic_year_id, academic_term_id, name, exam_type, start_date, end_date, status, created_at, updated_at, and deleted_at. It defines the exam event and connects it to the academic year and optional academic term. The status field supports stages such as scheduled, ongoing, completed, or cancelled.
The exam_results table stores marks for students in exam subjects. Its fields include id, school_id, exam_id, exam_subject_id, student_id, subject_id, marks_obtained, grade_scale_id, result_status, remarks, entered_by, created_at, and updated_at. The result_status field supports values such as pending, pass, fail, or absent. The entered_by field records the user who entered marks. This structure supports teacher-scoped marks entry and school-level result processing.
The activity_logs table stores user activity events. Its fields include id, school_id, user_id, module, action, description, subject_type, subject_id, ip_address, user_agent, and created_at. This table is append-only and records operational activity rather than full before-and-after data values. School Admin users can review own-school activity logs, while Super Admin users can review platform-level activity according to authorization rules.
The audit_logs table stores data-change evidence. Its fields include id, school_id, user_id, auditable_type, auditable_id, event, old_values, new_values, ip_address, user_agent, and created_at. Unlike activity logs, audit logs focus on data modification history. The old_values and new_values fields store structured change evidence. Audit records are immutable and append-only to preserve accountability.
The backup_logs table stores backup operation history. Its fields include id, school_id, backup_type, backup_scope, file_path, file_size_bytes, status, started_at, completed_at, generated_by, error_message, created_at, and updated_at. Backup access is restricted to Super Admin. Platform backups normally use platform scope, and backup files are treated as private resources rather than public downloadable files.
4.4 Multi-Tenancy Design
School Portal uses native Laravel multi-tenancy with a single database, shared schema, and school_id tenant key. The system does not depend on Stancl Tenancy, Spatie multi-tenancy, or any external tenancy package. Instead, it uses Laravel middleware, Eloquent global scopes, policies, services, and database relationships to enforce tenant boundaries. This approach supports a simpler and more explainable MCA project design while still demonstrating professional tenant isolation principles.
The school_id field is the primary tenant identifier. Every strict tenant-owned business table contains a non-null school_id. Examples include school_settings, academic tables, students, student_enrollments, attendances, fee tables, examination tables, and contextual system records where tenant ownership applies. The schools table acts as the tenant registry and is managed at platform level. Roles and permissions are platform catalog tables and do not receive school_id.
Tenant context is resolved from the authenticated user record. The system does not determine the tenant from a domain, subdomain, URL parameter, browser input, request header, or school selector. When a school-level user logs in, their user record contains the school_id that identifies their assigned school. TenantContextMiddleware validates the authenticated user, user status, role, school_id, and school activation state before establishing the Tenant context. If the user is a valid Super Admin with school_id as null, explicit Platform context may be established.
TenantContext has three states: Unresolved, Tenant, and Platform. In Unresolved state, no validated tenant or platform mode exists, so tenant-owned reads return no tenant rows and tenant-owned writes are denied. In Tenant state, queries are filtered to the authenticated user’s school_id, and tenant-owned creates receive the context school_id. In Platform state, authorized Super Admin workflows may perform platform-level operations, but policies and services still control access.
The BelongsToTenant mechanism is used for strict tenant-owned models. It registers a tenant global scope for queries, filters tenant data during Tenant context, permits authorized platform queries during Platform context, and applies default-deny behavior during Unresolved context. During creation, school_id is derived from TenantContext rather than accepted from browser input. This prevents users from forging ownership by submitting another school_id in a form or request.
Global scopes are used to avoid depending on manual where clauses in every query. If a model is tenant-owned, normal Eloquent queries automatically apply the active tenant filter. This reduces developer error and improves consistency. Route-model binding also benefits from tenant context because cross-school records resolve as not found instead of revealing that the record exists in another school.
Policies and service validation provide additional protection beyond the global scope. Permission codes only decide whether a user may attempt a category of action. They do not decide which record the user may access. For example, a Teacher may have permission to mark attendance, but the service must confirm that the section is directly assigned to the teacher’s active teacher profile. Similarly, an Accountant may access fee collection workflows, but cannot configure fee structures or access unrelated academic modules.
This design supports the central tenant isolation rule: a school user must never read or write another school’s records. It also supports platform administration without treating null school_id as an automatic bypass. Only a validated Super Admin in explicit Platform context may access platform-level workflows, and even then, policies and services remain active.
4.5 RBAC Design
The RBAC design of School Portal is based on four fixed canonical roles: Super Admin, School Admin, Teacher, and Accountant. The project does not implement custom role creation in the MVP scope. Role and permission records are system-managed, and the UI cannot create, delete, rename, or change the stable role codes. This fixed model keeps authorization clear, testable, and suitable for academic evaluation.
RBAC works together with tenant context. A permission grants only the possibility of performing an action. The actual record access is still controlled by tenant scope, policy checks, assigned class or subject boundaries, and service-layer validation. Therefore, RBAC is not used as the only security mechanism. It is one layer within the wider authorization design.
Super Admin users manage platform-level workflows such as school management, constrained role-permission mapping, platform reports, activity logs, audit logs, and backup management. School Admin users manage school-level operations for their own school. Teachers perform assigned academic workflows such as attendance and marks entry within assigned scope. Accountants perform financial workflows such as fee collection, receipts, payment history, outstanding balances, and financial reports.

4.6 Module Design Summary
The Authentication Module is designed as the entry point of the application. It provides login, logout, password reset, session management, and profile management. The design uses globally unique email login so that the user identity can be resolved before tenant context is established. After authentication, the middleware determines whether the user belongs to platform context or tenant context.
The School Management Module is designed for Super Admin use. It manages the tenant registry through the schools table. Super Admin users can create, update, view, activate, and deactivate schools. School deactivation preserves data while denying access to users of inactive schools. The design avoids exposing routine destructive deletion as a normal school operation.
The School Settings Module is designed for School Admin users. It stores school-specific preferences in the school_settings table. The module includes logo management, timezone, currency, academic year start month, attendance start time, grading system, and additional settings. School settings are tenant-owned and therefore automatically scoped to the active school.
The User Management Module is designed to manage authenticated users. Super Admin users manage platform-level and authorized school user workflows, while School Admin users manage users within their own school. The users table connects each user to a fixed role and, for school users, a required school_id. User status, session invalidation, and role assignment are handled with service and policy checks.
The Role & Permission Module is designed as a constrained RBAC workspace rather than an unrestricted authorization editor. The roles and permissions are system-managed. Super Admin can view mappings and edit non-essential mappings for school roles within the maximum canonical boundary. School Admin can view effective mappings and assign permitted school roles but cannot mutate shared RBAC rows. Teacher and Accountant users do not access this module.
The Academic Structure Module is designed around academic years, terms, classes, sections, subjects, and teacher profiles. These records form the academic foundation of the system. School Admin users manage academic structure for their own school, while Teachers receive limited visibility based on assigned sections and subjects. Academic records are strict tenant-owned records.
The Student Management Module is designed to separate student master records from enrollment records. The students table stores personal and admission information, while student_enrollments stores class, section, academic year, roll number, and enrollment status. This design allows the system to preserve student identity while tracking academic placement over time.
The Attendance Management Module is designed to store daily retained attendance records. Attendance is linked to the student, academic year, class, section, date, status, and marking user. School Admin users may manage attendance within the school. Teachers may manage attendance only for directly assigned sections. Attendance records are corrected and retained instead of casually deleted.
The Fee Management Module is designed around fee setup, student fee assignment, fee collection, receipt generation, outstanding balance tracking, and sandbox transaction evidence. School Admin users manage setup and assignments, while Accountants perform collection and financial workflows. Fee payments and transactions are retained financial history.
The Examination Management Module is designed to support exam setup, subject assignment, grade scales, marks entry, result processing, and report cards. School Admin users manage the complete own-school examination workflow. Teachers perform marks entry and view results only within assigned class and subject boundaries. Accountant users do not access examination workflows.
The Reporting Module is designed to generate role-aware and tenant-aware operational reports. Reports use filters, pagination, CSV export where applicable, and browser print views. School Admin reports are limited to own-school data, Teacher reports are limited to assigned academic scope, Accountant reports are limited to financial data, and Super Admin reports are platform-level and aggregate-focused where applicable.
The Dashboard & Analytics Module is designed to provide role-specific summaries. Super Admin dashboards show platform indicators. School Admin dashboards summarize students, attendance, fees, examinations, and activity for the school. Teacher dashboards focus on assigned classes, attendance, and marks entry. Accountant dashboards focus on collections, outstanding balances, transactions, and receipt summaries.
The Activity Log Module is designed to capture user actions. It stores the module, action, description, subject, actor, IP address, user agent, and timestamp. This supports operational traceability and helps administrators review how the system is being used.
The Audit Trail Module is designed to capture change evidence. It records old values, new values, event type, actor, and request metadata. Audit records are append-only and immutable. This supports accountability for important modifications.
The Backup Management Module is designed for Super Admin only. It records manual backup operations and backup history in backup_logs. Backup file paths are private, and School Admin users do not access Backup Management even though they may access own-school Activity Logs and Audit Trail.
4.7 UI and Screen Flow
The user interface of School Portal follows a role-specific screen flow. The common flow begins with the Login screen. After successful authentication, the system establishes tenant or platform context and redirects the user to the appropriate dashboard. The dashboard then presents authorized navigation menus based on role, permissions, tenant context, and module availability.
The global authenticated layout contains a header, sidebar, page header, content area, and footer. The header shows platform or school identity, active academic context where applicable, user role, notifications, and user menu. The sidebar contains module navigation. The content area displays forms, tables, dashboards, reports, charts, receipts, logs, or print views depending on the selected module.
Super Admin users enter a platform dashboard. The navigation includes Schools, Users, Roles & Permissions, Academic Structure read-only views where permitted, Reports, Analytics, Activity Logs, Audit Logs, and Backup Management. The dashboard widgets focus on platform-level information such as total schools, active schools, total users, recent platform activity, audit alerts, and backup status.
School Admin users enter a school dashboard. Their navigation includes School Settings, Users, Academic Structure, Students, Attendance, Fees, Examinations, Reports, Analytics, Activity Logs, and Audit Logs. The dashboard summarizes student counts, attendance status, fee status, examination status, and recent school activity. All data belongs only to the active school.
Teacher users enter a teacher dashboard. The navigation includes Students, Academic Structure, Attendance, Examinations, and Reports. The teacher dashboard focuses on assigned classes, today’s attendance, pending marks entry, and recent examination results. Menu visibility is limited to assigned academic responsibilities.
Accountant users enter an accountant dashboard. The navigation includes Fees and Reports. Dashboard widgets show today’s fee collections, outstanding fees, recent transactions, and receipt summaries. The Accountant interface is intentionally limited to financial workflows and does not expose academic setup, attendance, examination setup, logs, audit trail, or backup operations.
The UI design follows a maximum navigation depth of two levels. Menus are generated from user permissions, but hidden menu items are also protected by server-side authorization. This ensures that a user cannot bypass restrictions by manually entering a URL. Reports and dashboard widgets also follow role and tenant restrictions, so the interface does not summarize data that the user is not allowed to access.

4.8.2 Sequence Diagram — Login and Tenant Context
The login and tenant context sequence begins when the user submits email and password through the login form. The request reaches the authentication controller, which validates credentials against the users table. Since email is globally unique, the system can locate the identity before tenant context is established. If the credentials are invalid, the system rejects the login and records an appropriate activity event where applicable.
If the credentials are valid, the authentication flow checks the user’s status and role. For a Super Admin user, the system verifies that the user has the canonical Super Admin role and school_id as null. If valid, TenantContextMiddleware establishes explicit Platform context. For a school-level user, the system verifies that school_id exists, the referenced school is active, the school is not deleted, and the user role is valid for a school user. If these validations pass, TenantContextMiddleware establishes Tenant context using the user’s school_id.
After context is established, the request proceeds to route-model binding, policies, controller logic, service-layer workflows, and database operations. Tenant-owned model queries are filtered by TenantScope. The user is then redirected to the role-specific dashboard. At the end of the request, tenant context is cleared so that it does not leak into the next request, job, command, or test execution.

4.8.3 Activity Diagram — Attendance Entry
The attendance entry activity begins when a School Admin or Teacher opens the Attendance module. The system first checks authentication, role permission, tenant context, and policy authorization. If the user is a School Admin, the system allows attendance workflows for eligible students in active sections of the current school. If the user is a Teacher, the system verifies that the selected section is directly assigned to the teacher’s active teacher profile. Subject assignment alone does not grant attendance access.
After authorization, the user selects the academic year, class, section, and attendance date. The system loads the eligible student roster for that section from the current tenant. The user then marks each student with an allowed status such as present, absent, leave, late, or holiday where permitted. The system validates that each student belongs to the same school, has an active matching enrollment, and belongs to the selected section context.
When the user submits the attendance form, the service layer processes the records. Existing retained records are updated only through authorized correction workflows. New records are created with school_id from TenantContext, not from browser input. The system stores the attendance records, records activity and audit evidence where applicable, and then returns a confirmation message or updated attendance view to the user.
The activity diagram should show both successful and rejected paths. If the user is not authorized, if the section is not assigned to the teacher, if a forged school_id is submitted, or if the selected records do not belong to the active tenant, the workflow stops with an authorization or validation error. This demonstrates how tenant isolation, RBAC, and service validation are applied during a routine academic workflow.
